# ADR 0006: Rule Adjudicator Protocol を必須にする

- Status: Accepted
- Date: 2026-08-22

## Context

実験中、単純な File Search ではモデルが近視眼的な回答をしやすい問題が発生した。観測した具体例:

- setup 時の人数差をゲーム中の制約と誤解
- テーブル上の fish token 数と支払い fish 数を混同
- 1 箇所の記述だけから一般化
- 関連する example を確認せず回答

いずれも「最初に見つかった記述で答えてしまう」ことに起因していた。

## Decision

Rule 回答では Rule Adjudicator Protocol を prompt として明示し、必須プロトコルとして扱う。
**実験でこの prompt を与えたところ大きく改善した**ため、これを採用の根拠とする。

protocol が要求するもの:

- 結論を出す前に、基本ルール / 用語定義 / setup / player count 差 / 例外規則 / 資料内の例を順に確認する
- 1 つの記述のみを根拠に一般化しない
- 初期状態を定めるルールとゲーム進行中のルール、支払う資源と配置する資源、例示と規則を区別する
- 出典（ファイル名・ページ番号・原文）を明記する
- 資料に記載がなければ、その旨を明示して推測を公式ルールとして断定しない
- **根拠 → 分析 → 結論の順で示す（結論から先に書かない）**

prompt の本文は `src/tribunal/application/rule/prompts/adjudicator.md` に `.md` として置き、
コード内の文字列リテラルにしない。eval で前後比較する対象なので diff が review で見えることが要件。

## Consequences

- 回答が長くなる。結論だけ欲しいユーザーには冗長
- prompt が実装そのものなので、フォーマットを変えたいときは prompt を直す。spec 側に写さない
- 効果は実験で確認したが、数値では測っていない。eval を作るまで回帰を検出できない
- 「記載なし」の表現が prompt 内で複数ある（`資料から明確な記載はありません` / `記載が見つかりません` / `記載なし`）。
  assertion を書く段で 1 つに寄せる必要がある
