# ADR 0009: 明示タグを主経路にし、keyword は補助にする

- Status: Accepted
- Date: 2026-08-26

## Context

[0008](0008-no-hybrid-intent.md) で intent を 2 値 + Ambiguous と決めたあと、
実際にどう判定するかを決める必要があった。LLM に判定させると状態が増え、デバッグが難しくなる。

## Decision

判定は次の優先順位で行う。

```text
1. 明示タグ
2. keyword（rule / strategy の両方を 1 回で見る）
3. 既定 → Rule
```

**明示タグを主経路とし、keyword はタグを忘れた場合の推測**として位置づける。
したがって keyword の精度が甘くても実害は小さい。初期セットは当て推量であり、
実際の質問文を見て調整する前提。

タグの形式は行頭のみ。コロン形式を主、角括弧形式を alias とする。

```text
戦略: / strategy: / [戦略] / [strategy]    → Strategy
ルール: / rule:   / [ルール] / [rule]      → Rule
```

両形式を受けるのは、**日常的に打つ形と確実に効かせたい形で求めるものが違う**ため
（コロンは打鍵が軽く IME でも近い / 角括弧は誤検出がほぼない）。
行頭限定にすれば曖昧さは形式の数に依存しないので、alias を増やすコストは実質ゼロ。

`/strategy` のような slash command 風の形は採らない。**Slack が行頭の `/` を横取りする**ため
送信前に弾かれ、将来 slash command を実装するときに名前も衝突する。

keyword は rule と strategy の両方を 1 回で評価し、**片方だけ当たれば決定、両方当たれば Ambiguous** とする。
曖昧だった事実を消さない。

判定後、タグは質問文から除去して retriever へ渡す（タグが検索クエリに混ざると検索結果が劣化する）。

タグを付けずに投げた場合は、**どちらとして処理したかを回答に添える。**
運用ルールを事前に説明しなくても使いながら覚えられ、判定が壊れていることが使用中にすぐ分かる。
タグを明示した場合は付けない（ユーザーが既に知っている情報なので）。

判定方式は keyword → 将来の LLM で実装が 2 つになることが確定しているため、
「port を切るのは retrieval だけ」の例外として `IntentClassifier` Protocol を置く。
置き場所は `application/pipeline/`。`ports.py` は adapter から見た差し替え点なので層が違う。

## Consequences

- タグを付ければ確実に意図通りに振れる
- keyword の調整は「よくある取りこぼし」を見てから行う。事前に完璧を目指さない
- untagged の回答には毎回 1 行の注記が付く。慣れたユーザーには冗長
- LLM 判定の実装は Protocol の口だけ空いていて、まだ無い
